Every prompt sent to a text model or an image model, how it is assembled, and which knob changes what.

The goal: when you want to tweak something the model says or draws, find the exact string, know what feeds into it, and know what else re-uses it before you change it. Companion to architecture.md. There are exactly two families – text prompts (all in lib/text.js, each returns a JSON blob) and image prompts (assembled in server.js, one image out).

leverage / injection point marks a spot where kid input flows in, or a constant you can turn to change every generation. The green chips below and in the diagram are the same idea: these are the knobs. Everything else is plumbing.

The flow, end to end

Every button a kid presses runs the same two-beat pipeline: a text call that returns a JSON creature (or trainer dossier), then an image call that draws it. The green chips are where you steer the result.

Part A – Text prompts lib/text.js

Every text call is { system, user } → a raw string that must parse as JSON (callJSON, 3 attempts). The system prompt is shared by all four calls; the user prompt is what differs per flow.

A0. The shared system prompt every call

Source: SYSTEM + buildSystem().

You invent silly Pokemon-style creatures for a kid aged 12-14.
Humor: silly and gross-out humor is great. Keep everything PG and kind, but add a degree of cinematic realism.
Always answer with pure JSON only, no markdown fences.

If env CANON_FILE points at a file, its contents are appended as ## Universe canon\n<file>.

Tweak points: age band, humor, tone – edit SYSTEM. House lore that colors every generation – put it in CANON_FILE, don't inline it. SYSTEM CANON_FILE

A1. The stage schema stageShape() · Create + Evolve

Both Create and Evolve end with Reply with JSON: <stageShape(…)>. The only things that change between calls are the two number ranges (HP band, damage band), from the stage number or the variant's band.

FieldInstruction summary
nameUse the kid's name idea if given; punny portmanteau of a trait + animal/object word. For evolutions, keep the root word and escalate the modifier.
category"The X Pokemon".
types1–2 of the 18 canon types (listed inline).
hpIn the band, multiple of 10. Band depends on stage/variant (below).
flavorOne silly Pokedex sentence.
movesExactly 2, each {name, damage, text}; damage in the band, multiple of 10.
artPromptDetailed visual prompt for the image model. Must end with the shared ART_STYLE.
descriptionCompact visual description (colors, shapes, features) for reuse in later prompts.
backstory3–5 sentence funny origin; ground it like a half-forgotten folk legend when it fits.

The HP and damage bands are the whole numeric variant system:

Important: the prompt only asks for numbers in these bands. clampStage() then forces them in code (rounds to tens, clamps to the band, makes each evolution beat the prior HP by ≥10). Editing a band changes both the ask and the guarantee – edit the band in STAGES, not the prose. STAGES.hp / .dmg

A2. Create newPokemon

Called by POST /api/pokemon. Always stage 1, never a variant. The only runtime piece is the kid's raw prompt.

A kid wants a new Pokemon: "<kid's prompt>".
Invent stage 1 of it. Reply with JSON: <stageShape(1, null)>

A3. Evolve evolvedStage

Called by POST /api/pokemon/:id/evolve. Richest text prompt, most variants. Bracketed pieces are conditional.

This Pokemon: <JSON of prev stage: name, category, types, hp, description, backstory>
Invent its next evolution stage: bigger, more powerful, clearly the same species, sillier if possible.
[The kid wants the evolution to be: <guidance>.]        <- only if the kid typed guidance
[This is a rare <VARIANT> mega-style evolution -         <- only on a rolled special (stage 3)
 dramatically more powerful and epic.
 Have this picture include an appropriate scenic background.]
HP and move damage must be higher than before (hp was <prevHp>).
Write a NEW backstory that clearly continues the previous stage's.
Reply with JSON: <stageShape(stageNo, variant)>
  • Previous-stage context – always injected as JSON, so the model stays on-species.
  • Guidance – optional text the kid typed before EVOLVE. Absent → the line is dropped.
  • Variant – rollSpecial(3) result. Absent → the whole variant block is dropped and stageShape uses the normal band.
  • prevHp – forces the "higher than before" instruction to be concrete.
The variant word in the text prompt is the object key (VMAX / EX / Mega), which is why the text prompt reads "rare Mega mega-style evolution" for Mega. If that phrasing bugs you, that's the seam.

A4. Trainer profile trainerBackstory

Called on trainer create and on first profile view (backfill). A trainer dossier, not a creature.

A Pokemon trainer named "<name>", described as: "<description or 'a mysterious trainer'>".
Invent their profile. Their finishing move MUST be picked from this list of devastating canon moves
(name, type, power): <FINISHER_MOVES joined with '; '>.
Their favorite Pokemon MUST be a Pokemon that canonically uses that move (signature Z-moves belong to
their signature Pokemon). Pick a pairing that fits this trainer's personality.
Reply with JSON:
{"region": "...", "homeGym": "town + gym type", "backstory": "3-5 sentences mentioning region and gym",
 "favoritePokemon": "...", "finishingMove": "the move exactly as listed"}

FINISHER_MOVES is a hard-coded list of every canon move with power > 150 (NotebookLM "Pokemon moves" source, cached 2026-07-13). Edit the list to change the pool of finishers.

Part B – Image prompts server.js

Assembled in server.js (one per flow), pulling shared art fragments from lib/text.js and the continuity helper from lib/providers.js. Three fixed fragments recur.

B0. The shared art fragments

ART_STYLE (lib/text.js) – the house look, appended to every artPrompt by the text model:

Cel-shaded official Pokemon-style game art in the Ken Sugimori watercolor style: simple readable
silhouette, bold slightly-varied outlines, 1-2 midtone main colors plus one accent, soft purple-tinted
shadows, basic highlights, full body, single creature, plain white background. Do not write the creature's
name or any text, letters, numbers, logos, or watermarks anywhere in the image. Do your best to honor
specifics and intent of the kid's prompt.

NO_TEXT (server.js) – a shorter no-text reminder re-appended on Evolve and Alter:

Do not write the creature's name or any text, letters, numbers, logos, or watermarks anywhere in the image.

Variant art phrases (STAGES.special.variants[tier].art) – appended when a stage is/was a special:

TierArt phrase
VMAXcrackling electric-blue energy, radiant silver aura, sparks flying, dynamic stadium background with storm-lit clouds and lightning
EXwreathed in golden fire, glowing prismatic divine radiance, radiant sunburst temple background
MEGAcolossal mega-evolved form, swirling cosmic nebula background that emphasizes the huge scale of it, rainbow prismatic aura, glowing mega stone on its brow
VMAX and EX gained their scenic backgrounds in the 2026-08-30 commit "add background art to VMAX and EX variant image prompts"; before that they only described an aura and rendered on plain white. Mega already carried its cosmic-nebula background. STAGES.special.variants[tier].art

withContinuity(provider, prompt, description) (lib/providers.js) – if the provider has no reference-image support and a description exists, appends \nThe creature looks like this: <description>. Otherwise returns the prompt unchanged (reference-capable providers get the actual prior image instead).

Bridge-only suffix – the bridge provider appends \nSquare image, 1:1 aspect ratio. when it writes the job (writeBridgeJob). Gemini/z.ai set 1:1 via the API config instead.

B1. Create image prompt POST /api/pokemon

<withContinuity(provider, artPrompt, '')>
The kid asked for: <kid's prompt>.
  • artPrompt is what the text model just produced (already ends with ART_STYLE).
  • The description arg is empty, so withContinuity is a no-op on create.
  • The kid's original words are re-stated to the artist as a final intent nudge.

B2. Evolve image prompt POST /api/pokemon/:id/evolve

<withContinuity(provider,
  "Evolve this creature. Its evolved form: <artPrompt>
   Same species, same color palette, same art style, clearly a bigger more powerful evolution.
   The evolved form should look sturdier or sharper than before, same palette, keep one signature feature.",
  <prev stage description>)
[The kid asked for: <guidance>.]        <- only if guidance was typed
[<variant art phrase>.]                  <- only on a rolled special
<NO_TEXT>

Separately from the prompt text: if the provider supportsReference, the previous stage's image file is attached as a reference. That is the strongest continuity lever – only Gemini/mock use it; zai and bridge fall back to the description injected by withContinuity. All three variants (guidance, variant art phrase, reference-vs-description) can stack at once on a Gemini stage-3 special evolution with kid guidance.

B3. Alter / Redraw image prompt POST /api/pokemon/:id/alter

The most conditional prompt. The base clause depends on whether the kid typed anything.

With instruction:

<instruction>. Keep it the same creature, same cel-shaded Pokemon-style game art, full body, plain white background.

Blank (redraw my original):

Draw this creature fresh: <stage 0 uses the kid's original words; later stages use the stage description>

Then, conditionally:

  • If there's no reference image and a description exists and it isn't already in the base clause, append \nThe creature looks like this: <description>.
  • If the stage is/was a special, append \n<variant art phrase>. (a redraw keeps its foil look).
  • Always append \n<NO_TEXT>.

Reference image: used when the provider supports it and the current art isn't the mock placeholder (a <500-byte file is treated as "no real art to draw from").

Side effect: an instructed alter appends Recently altered: <instruction>. to the stage description, so subsequent no-reference prompts inherit the change. (Marked ponytail: in code as a naive continuity note – a vision re-caption would be the upgrade if drift ever matters.)

B4. Trainer avatar prompt POST /api/trainers

Fixed, no variants beyond the kid's description:

Pokemon trainer portrait: <description>. Friendly bust portrait, cel-shaded Ken Sugimori watercolor style,
plain white background. Do not write any text, letters, numbers, logos, or watermarks in the image.

If you'd like to…

Task-first recipes. Each names the one edit that does it and the file it lives in.

If you'd like the creatures goofier or grosser

Loosen the humor line in SYSTEM ("silly and gross-out humor is great") and drop "add a degree of cinematic realism".

lib/text.js · SYSTEM

If you'd like the art more epic / more realistic

Edit ART_STYLE – it's appended to every artPrompt, so one change moves the whole house look. Keep the "no text/watermark" clause.

lib/text.js · ART_STYLE

If you'd like specials to be rarer (back to ~5%)

Lower STAGES.special.odds. They're absolute and currently sum to 0.35; make them sum to ~0.05 (e.g. VMAX .02, EX .02, Mega .01).

lib/text.js · STAGES.special.odds

If you'd like stronger (or weaker) starters

Move the Stage 1 band. STAGES.hp[1] / STAGES.dmg[1] set both the ask and the clampStage guarantee.

lib/text.js · STAGES.hp / .dmg

If you'd like a new lane (GX, Gigantamax, Shiny)

Add a key to odds and a matching entry in variants (stats + art phrase), then add VARIANT_LABELS + a .dv-<tier> / .variant-<tier> style block. Re-check the odds total.

lib/text.js + public/card-format.js + style.css

If you'd like specials to stop adding scenic backgrounds

Trim the background clause out of each variants[tier].art string (the part after the aura), and remove "include an appropriate scenic background" from evolvedStage.

lib/text.js · variants[tier].art + evolvedStage

If you'd like a different pool of trainer finishers

Edit FINISHER_MOVES. Keep the "Name (Type, Power)" shape – the prompt tells the model the favorite Pokemon must canonically use the chosen move.

lib/text.js · FINISHER_MOVES

If you'd like tighter visual continuity across evolutions

Use a reference-capable provider (gemini/mock): its previous-stage image is attached directly. Description-only providers (zai/bridge) rely on the text description field, so make that field richer.

lib/providers.js · supportsReference

If you'd like to change the universe lore

Don't inline it – edit the CANON_FILE (docs/reference/canon-pack.md). It's injected into the system prompt on every text call. Re-distill it from sources with scripts/refresh-notebook-cache.py.

.env CANON_FILE + docs/reference/canon-pack.md

If you'd like to reword what "evolve" means to the artist

Edit the "Evolve this creature… keep one signature feature" template in the evolve route. That's the text handed to the image model, distinct from the text-stage evolve prompt.

server.js · evolve route

If you'd like the model to stop drawing text on cards

The no-text rule lives in two places: ART_STYLE (create) and NO_TEXT (evolve/alter). Strengthen both, or add it to the trainer-avatar prompt in server.js.

lib/text.js ART_STYLE + server.js NO_TEXT

If you'd like square art without the bridge suffix

Gemini/z.ai already set 1:1 via API config. The bridge provider appends "Square image, 1:1 aspect ratio." in writeBridgeJob – change it there if the driver handles aspect differently.

lib/providers.js · writeBridgeJob

If you'd like evolutions to allow a 4th stage

The 3-stage cap is enforced in the evolve route (stages.length >= 3), and rollSpecial only fires into stage 3. Both would need to move together.

server.js evolve route + lib/text.js rollSpecial

If you'd like editable stats after generation to widen

The PATCH route whitelists name, hp, flavor, moves, category (plus per-stage backstory). Add a field to that list to make it editable from the card.

server.js · PATCH /api/pokemon/:id
